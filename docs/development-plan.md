## 一、背景：为什么这份计划与最初的项目书不同

原始项目书的核心构思（体育专业标准 + AI + 传播学，三学科交叉）是成立的，但经过
调研，有 **5 处硬事实必须修正**，否则会在答辩现场被问穿：

| # | 项目书原文 | 调研结论 | 影响 |
|---|---|---|---|
| 1 | 「Jev 轻量决策模型」 | Jev 真实存在（TypeSafe AI，2026-09-15 发布），但**闭源云 API、只吃文本、有报道称未向中国大陆开放**；厂商宣传的速度倍数已被第三方实测质疑 | **不能作为离线答辩依赖** |
| 2 | （未提及） | **改用 Laya**（Convai Innovations，2026-09 开源，Apache 2.0，421M/322M 编码器）——与 Jev 同构的 `choice/score/noul` 三原语，但**权重开源、可自部署、可微调** | 决策层可完全离线，且「自建数据集微调开源决策模型」是更硬的原创贡献 |
| 3 | 「MediaPipe 提取 **17** 个人体骨骼关键点」 | BlazePose 是 **33 点**（17 点是 COCO 标准，是 33 点的子集）。33 点多出脚跟/脚尖/手部点，**对深蹲膝踝对齐、立定跳远起跳判定是必需的** | 按 17 点设计会丢掉关键特征，必须按 33 点重做特征层 |
| 4 | 「青少年体质大数据可视化大屏」 | 保留，但**必须与 App 分层**——ML Kit / MediaPipe 均不支持 Web，推理只能在手机上 | App 负责采集+判定，笔记本负责大屏+决策，见第三节架构 |
| 5 | 「HSE 顾问负责 **Jev 的 Prompt 工程**」 | Laya/Jev **不是 Prompt 驱动的**，是类型化决策 API（给候选集，返回概率分布），没有「提示词工程」这回事 | 申报书里的措辞要改成「**决策阈值设计 + 微调配方 + 温度校准**」，否则评委一问就露怯 |

### 最关键的一条风险（必须先说）

**Laya 的中文能力出厂状态不可用。** 第三方实测：

- 中文准确率 **47.7%**（对比英文短题 95.8%）
- 40 条中文工单对比：Laya 本地 **57%** vs Jev API 78%
- **错误回答的置信度高达 0.91**（校准前完全不可信）
- 已知缺陷：位置偏差（「50 道多选题有 46 道选 A」）、选项数 >20 后准确率急剧下降、
  `score` 原语最弱

**但开源仓库 `chinese-laya` 已证明中文微调可把一致率从 34% → 75%+。** 因此本项目把
「**自建青少年体测动作决策数据集 → 微调 Laya → 温度校准**」提升为**核心工作流**，
而不是可选项。这同时是评分表里「创新性与原创贡献」和「完成度与可验证性」最扎实的
得分点 —— 因为它有基线、有提升曲线、有 ECE 对比、可复现。

## 二、已确认的决策

| 项 | 决定 |
|---|---|
| 交付形态 | 手机 App（Flutter），Android 真机为主，iOS 顺带兼容 |
| 姿态后端 | Flutter + `google_mlkit_pose_detection`（bundled，完全离线） |

## 三、系统架构

```
┌───────────────────────────────────────────────────────────┐
│  手机 App（Flutter + ML Kit Pose）        【完全离线】      │
│                                                           │
│  相机 → 33 关键点 → 关节角度特征 → 规则引擎 → 状态机计数    │
│                                                           │
│  ┌──────────────┐  ┌──────────────┐  ┌────────────────┐  │
│  │ 姿态后端接口  │  │ 领域层        │  │ 本地兜底决策    │  │
│  │ MLKit│MediaPipe│ │ 特征+状态机   │  │ 纯规则，无 Laya │  │
│  └──────────────┘  └──────────────┘  └────────────────┘  │
└──────────────────────────┬────────────────────────────────┘
                           │ HTTP（手机热点 / 局域网）
                           │ 传输：结构化特征 JSON（不传视频）
┌──────────────────────────▼────────────────────────────────┐
│  笔记本 Flask 服务                          【完全离线】    │
│                                                           │
│  ┌────────────────┐  ┌──────────────┐  ┌───────────────┐ │
│  │ laya-serve     │  │ 方案库        │  │ 文案模板库     │ │
│  │ 127.0.0.1:8000 │  │ 错误→矫正方案 │  │ 按年龄段       │ │
│  │ choice/score/  │  │ 年龄/禁忌过滤 │  │ 分版本         │ │
│  │ noul           │  │              │  │               │ │
│  └────────────────┘  └──────────────┘  └───────────────┘ │
│                                                           │
│  持久化：SQLite / MySQL    报告生成：PDF                   │
└──────────────────────────┬────────────────────────────────┘
                           │
┌──────────────────────────▼────────────────────────────────┐
│  Web 大屏（Vue3 + ECharts）                  【离线 dist】  │
│  全国体质热力图 / 时序变化 / 指标分布 / 点击下钻            │
└───────────────────────────────────────────────────────────┘
```

**设计要点：**

1. **决策层按「组」调用，不按帧。** 一次深蹲 10 个做完才调一次决策 → 延迟预算 1–2 秒
   完全够用，2 核 CPU 的性能瓶颈不致命。
2. **降级链路是答辩保命的**：网络断了 → 手机本地规则引擎仍出结果（只是没有 Laya 的
   置信度校准与方案择优）。Demo 时故意演示一次断网降级，反而是加分项。
3. **只传特征不传视频** —— 既是隐私合规（未成年人敏感个人信息），也规避了局域网
   带宽问题。
4. **姿态后端做成可替换接口**，默认 ML Kit，保留 MediaPipe 后端，答辩可讲
   「双后端可切换」。

## 四、技术选型

| 层 | 选型 | 版本/说明 | 风险 |
|---|---|---|---|
| App 框架 | Flutter | 3.44+（`google_mlkit_pose_detection` 0.16.x 要求 ≥3.44） | 团队需学 Dart |
| 姿态检测 | `google_mlkit_pose_detection` | 0.16.x，**bundled 模式**（模型编进 APK，不依赖 Google Play Services，断网可用），33 点 | 插件自标 Beta；无世界坐标 |
| 相机 | 官方 `camera` 插件 | Android 显式 `ImageFormatGroup.nv21`，iOS `bgra8888` | 帧格式错误会直接报错/黑屏 |
| 决策层 | Laya | **`laya-multilingual`**（mmBERT-base，322M，1024 上下文，100+ 语言）——**不要用英文版 `laya`**，对中文直接失效 | 版本两周内从 0.1.1 跳到 0.3.x，**必须锁版本** |
| 决策服务 | `laya-serve` | 提供 Jev 兼容协议 `POST /v1/systemone`，默认监听 `0.0.0.0:8000` 且**无鉴权** | 必须显式绑 `127.0.0.1` 或加 API key |
| 后端 | Python + Flask | 团队已有技能 | — |
| 数据库 | SQLite（开发）/ MySQL（演示） | — | — |
| 大屏 | Vue3 + ECharts | 团队已有技能 | — |

### 明确的排除项及原因

- **YOLO11-pose**：AGPL-3.0，传染性许可证，竞赛项目慎用
- **`laya-mnn` 做手机端侧**：是 Python 包、无 Android 案例、且存在「Metal 后端与降精度
  CPU 路径返回全零 logits」的已知缺陷 → **不采用**
- **Jev 云 API**：不能离线、大陆访问不确定 → 仅作为答辩时的「范式对照」讲解，不进代码路径
- **手机端侧跑 Laya**：322M 模型即便 LiteRT 转换后仍需 ~680MB，且无团队可复用的验证案例
  → v1 不做（若后期有余力，`litert-community/Laya-Multilingual-LiteRT` 有现成 Kotlin
  示例，Galaxy S26 实测端到端约 60ms，是明确的升级路径）

### 国内环境必做配置（第一周就要验证）

```
PUB_HOSTED_URL=https://pub.flutter-io.cn
FLUTTER_STORAGE_BASE_URL=https://storage.flutter-io.cn
```

- Gradle 仓库换阿里云镜像、Gradle 发行版换腾讯镜像 → 具体配法与实测见
  [phase0-environment.md](phase0-environment.md) 二
- Laya 权重下载走 **ModelScope**（HF 直连在国内常超时）
- 已知坑：装了 TensorFlow 会导致 transformers 导入死锁 → 设 `USE_TF=0`

### 需要尽早核定的体育阈值（否则工程无法收口）

**大量体育阈值找不到权威来源，必须由武体队长依据国标口径 + 学生群体实测核定**，
包括：深蹲合格深度切点、膝内扣学生人群切点、俯卧撑体线角、平板支撑统一采用值、
各组级评级权重等。这些**不允许工程师凭空填数字**。

产出的阈值表须带 `source_type` 字段（国标/文献/待核定）与版本号，统一管理。
当前 `shared/thresholds/` 里的 13 条**全部是 `pending_review`** —— 这不是遗漏，
而是诚实的状态：系统现在能跑、能出提示，但**不能扣分**。

## 六、分期计划（15 周）

### Phase 0 · 环境搭建与技术验证（第 1 周）⭐ 最关键

**目标是「尽早证伪」** —— 如果 Flutter 路线的实时帧率不达标，必须在第 1 周就知道，
而不是第 10 周。

- 安装 Flutter SDK / JDK 17 / Android SDK，配置国内镜像
- 真机跑通帧率探针（见文首说明：取代了原计划的「官方 example」）
- 笔记本跑通 `pip install laya` + 一次 `choice` 决策，权重从 ModelScope 拉取
- **验收标准**：
  - 手机实时出 33 点骨架，**稳定 ≥15 FPS**（推理帧率，非预览帧率）
  - 笔记本一次决策返回时间 **< 2 秒**，内存峰值实测记录
  - 首帧延迟、发热情况记录在案
- **决策点**：若帧率不达标 → 降分辨率到 480p / 换 lite 模型 / 或退回原生 Android + MediaPipe

### Phase 1 · 领域层 + 单动作闭环（第 2–4 周）

  像素坐标再算角度**（否则宽高比失真）
- 深蹲状态机：`CALIBRATION → STANDING → DESCENT → BOTTOM → ASCENT`，含滞回阈值 +
  最短停留 + N-of-M 投票防抖

### Phase 3 · 决策服务 + 多动作（第 6–9 周）

- Flask + laya-serve 集成（显式 `127.0.0.1` + API key，不留无鉴权端口）
- 方案库：错误类型 → 矫正动作映射（臀桥、蚌式开合、弹力带侧向行走、靠墙静蹲、箱式蹲、
  膝触墙踝背屈、死虫式、鸟狗式等），带年龄段/器材/禁忌/难度字段，经武体队长核定后上线

- 扩展到 3–4 个动作：深蹲 → 开合跳 → 俯卧撑 → 平板支撑（均为非国标训练项目，
  姿态可完整判定）
- **重要边界**（必须写进产品文案，避免误导）：
  - 国标 10 个正式测量项中，纯姿态能完整测成绩的只有仰卧起坐、引体向上、跳绳（估算）
  - **立定跳远、坐位体前屈只能做「规范性评分」，测不出厘米成绩**（单目无标定，
    世界坐标原点在髋部，给的是相对量）
  - **50米跑、800/1000米、肺活量、BMI 做不了**，App 只承接成绩录入与评分换算
- **验收标准**：手机拍 → 特征传笔记本 → Laya 返回主问题 + 严重度 + 方案 → PDF 报告生成，
  端到端跑通

> 截至 2026-10-04：**这条链路的前半段已通，且是在 `rule-only` 降级路径上通的** ——
> 决策服务不连数据库、不需要 key，那个要吃 1GB 权重的 `laya-serve` 不起也照常返回
> 完整响应（`meta.decision_model_version="rule-only"`，端侧据此在报告里披露
> 「这份结论由规则引擎直接给出，没有经过决策模型判断」）。
> 手机侧的连接走 `adb reverse tcp:8080 tcp:8080`，服务照旧只绑 `127.0.0.1`。
> 尚未做的是 **PDF 报告**（端侧目前只在屏上渲染）与**多动作**。
>
> 自 2026-10-04 起，这条链路**不再要求「手机和笔记本在一起」**：连不上服务时端侧
> 在本机跑同一条规则路径（`app/lib/app/local_decision.dart`），报告照出、顶部标明来源。
> 判据是「服务端有没有给出答复」，所以 `adb reverse` 没搭好、地址填错这类问题
> **仍然会照旧报错**，不会被兜底盖住。器材选择界面还没做，本机判定暂时一律按徒手算。

## 八、验证方式（怎么证明这东西真的能跑）

**开发期**

- 领域层写单元测试：喂入录制好的关键点序列，断言角度值与状态转移
- **跨语言一致性**：`shared/fixtures/` 的 golden 测试向量是 Python 与 Dart 两份实现的
  唯一裁判（8 个场景 × 24 个特征，容差 1e-4）
- 决策层写回放测试：`decisions` 表留存每次调用的输入输出，可离线回放与回归对比

**答辩前**

1. **离线全链路演练**：断开外网，笔记本开热点，手机拍 → 笔记本决策 → 大屏显示 → 导出 PDF
2. **模型评测可复现**：一条命令跑出「基线 / 微调 / 微调+校准」三栏对比表（一致率 + ECE）
3. **动作判定准确率**：在留出测试集上报告各错误类型分类的准确率/召回率，附混淆矩阵
4. **性能实测记录**：目标演示机上的推理 FPS、内存峰值、连续运行 5 分钟的帧率衰减曲线

**必须保留的可核验材料**

- 公开数据集来源清单 + 许可证文件
- 测试集划分文件与随机种子
- 阈值表（带来源类型与版本号）
- 微调超参配置、训练日志、GPU 租用记录
- 校准前后的 ECE 对比
