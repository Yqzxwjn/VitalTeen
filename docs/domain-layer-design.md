## 0. 定位与三条铁律

本层负责把「33 个骨骼关键点」变成「动作规范性判定」，是整条链路中唯一含体育专业知识的环节。

**铁律一：角度必须在像素坐标下算。** 归一化坐标 `x,y ∈ [0,1]` 分别按图宽、图高折算，直接在该空间算角会被画幅宽高比扭曲。所有角度类特征先还原为 `(x·W, y·H)` 再计算（见 §1.2）。

**铁律二：不可用的特征必须输出 `null`，不得降级填充。** 世界坐标缺失、关键点可见性不足时，依赖它的特征一律置空并在决策请求中显式声明，让决策层知道该降权或弃权。宁可弃权，不可编造确定性。

**铁律三：本层不产生任何体育阈值。** 阈值全部来自 `server/` 的阈值表（见 §7）。本层只做几何计算与规则执行。

- **脚跟 29/30 与脚尖 31/32** — 深蹲的脚跟离地判定、立定跳远的起跳前离地判定，没有这两个点做不了

> **常见错误**：项目早期文档写的"17 个关键点"来自 COCO 标准。按 17 点设计会丢失脚跟/脚尖，导致深蹲脚跟离地和立定跳远起跳判定无法实现。

### 1.2 坐标系的两条硬约束

**约束 A — 角度计算前必须还原像素坐标**

```
pixel_x = normalized_x * frame_width
pixel_y = normalized_y * frame_height
```

`frame_width` / `frame_height` 由相机采集分辨率提供，**必须随特征一起传入本层**，不得由本层猜测或写死。

**约束 B — 世界坐标不是"更好的坐标"，是"另一种坐标"**

| | 归一化坐标 | 世界坐标 |
|---|---|---|
| 原点 | 画面左上角 | 双髋中点 |
| 单位 | 无（0–1） | 米 |
| 可用性 | 两种姿态后端都有 | **仅 MediaPipe 有，ML Kit 没有** |
| 适用 | 角度类特征 | 位移/高度类特征 |

**世界坐标原点在髋部**，意味着它给的是"相对人体的量"——可以回答"髋下蹲到膝以下了吗"，**不能**回答"跳了多远""前屈推了几厘米"。任何绝对距离都不在能力范围内，不要设计这类功能。

**约束 C — 世界坐标的 z 轴不可靠**

第三方评估显示 z 的准确率显著低于 x/y。z 只用于低权重的辅助判断（如"手是否在肩正下方"），**不得作为主要特征**。

### 1.3 特征可用性矩阵

本层每一项特征都必须声明其坐标系依赖。运行时若依赖不满足 → 输出 `null` + 在 `pose_quality` 中记录原因。

| 特征类 | 坐标依赖 | ML Kit 后端是否可用 |
|---|---|---|
| 关节夹角（膝/肘/肩/髋） | 像素坐标（约束 A） | ✅ |
| 躯干倾角、肢体倾角 | 像素坐标 | ✅ |
| 左右对称指数 | 像素坐标 | ✅ |
| 距离比（归一化到躯干长） | 像素坐标 | ✅ |
| 额状面膝角（FPPA 式） | 像素坐标 + 正视机位 | ✅ |
| 下蹲深度（髋相对膝的高度差，米制） | 世界坐标 | ❌ 降级为角度判定 |
| 脚跟抬升量（米制） | 世界坐标 | ❌ 降级为像素比值（需侧拍） |
| 跳跃高度（米制） | 世界坐标 | ❌ 降级为振幅比，仅评节奏 |
| 米制速度 | 世界坐标 | ❌ 改为周期/节奏类时间特征 |
| 空间前后关系（手在肩下？） | 世界坐标 z | ❌ 用正视+侧视分别校验 |

**降级不是失败**：对深蹲、开合跳、平板支撑、俯卧撑这些**角度主导**的动作，ML Kit 的降级方案完全够用。只有需要绝对位移的动作才受影响，而那类动作本就不在本项目范围内。

#### 待办：两条「矢状面量」没有做机位门控（2026-10-04 发现）

`views` 字段已经能表达机位依赖，目前**门控到位**的只有：

| 特征 | `views` |
|---|---|
| `heel_rise_ratio_*`（脚跟抬升） | `sagittal` `oblique45` |
| `body_line_angle`（体线角） | `sagittal` `oblique45` |
| `body_line_offset_ratio`（体线偏移，带符号） | `sagittal` `oblique45` |
| `shoulder_height_ratio`（肩比踝高多少） | `sagittal` `oblique45` |
| `frontal_knee_angle_*` / `frontal_knee_offset_*` / `frontal_knee_angle_max` | `frontal` |
| `pelvis_offset_ratio` | `frontal` |
| `leg_spread_ratio`（开合跳「开得够不够」） | `frontal` |

（对应 fixture `standing_frontal_valgus`：锁定"正视下额状面可用、侧视特征须判机位不匹配"。）

`leg_spread_ratio` 的门控**刻意只写 `frontal`，不带上 `oblique45`** —— 45° 下
分子（两踝横向间距）与分母（肩宽）的 `cos` 因子一阶相消、比值仍近似成立，但那只到
一阶为止：透视（肩比踝离镜头近）、躯干前倾让肩线与踝线不在同一深度、以及 45° 下
远侧腿常被近侧腿挡住，这三条会把比值推出百分比级的偏差，而且偏差随姿态漂。
多声明一个用不上的机位，只会让「这个特征在 45° 下也能用」变成一个错误的暗示。

但**深蹲另有两条规则吃的是没有门控的特征**：

| 规则 | 特征 | 物理上属于 | 现门控 |
|---|---|---|---|
| `INSUFFICIENT_DEPTH` 下蹲深度不足 | `knee_angle_L` | 矢状面 | **无** |
| `EXCESSIVE_TRUNK_LEAN` 躯干过度前倾 | `trunk_lean` | 矢状面 | **无** |

**风险**：正视机位下这两个特征照常算出数值，但数值没有意义 —— 下蹲时大腿指向镜头、
投影长度塌缩，投影膝角不再是深度；躯干前倾是矢状面量，正视下前倾方向指向镜头、
投影几乎不变，**前倾会被系统性低估**。表现为「看起来正常、其实是错的」，
正是本层在别处一直防的那类错误（见 `FeatureValue.unavailable` 的"绝不填 0"）。

**而且注释与实现已经不一致**：`domain/exercises/squat.dart` 的模块注释写着
"下蹲深度、躯干前倾、脚跟离地都是矢状面量"，可前两者并没有按矢状面门控。

**为什么不在 Phase 0 顺手改**：它牵动 `shared/` 下 Python 与 Dart 两份实现
加 `feature_conformance.json` 三方一致（§8），必须同改 + 同重建 fixture。
而 Phase 0 的探针根本不走领域层，改它不影响当前验证。

**Phase 1 收口时二选一**：

1. 给这两个特征补 `views: [sagittal, oblique45]`，正视下报 `view_mismatch`；或
2. 保留全机位，但**正视下的深蹲只报膝内扣与左右不对称**，并在结果里显式声明
   「深度与前倾未评估」。这条更贴合产品 —— 正视是默认机位（用户要看着屏幕做动作）。

无论选哪条，都先要真机确认 `hip_height_ratio`（同样无门控）在正视下是否真的可用：
它测髋相对躯干的高度比，不依赖矢状面投影，**可能本来就跨机位成立**。
若成立，深度规则可以改用它做正视机位的判据，而不是把这条规则整体关掉。

## 2. 特征算子

### 2.1 基础算子

| 算子 | 定义 | 备注 |
|---|---|---|
| `angle3(a, b, c)` | 顶点 b 处，向量 BA 与 BC 的夹角，`arccos((BA·BC)/(|BA||BC|))` | 输入必须是像素坐标 |
| `tilt(v)` | 向量与竖直方向的夹角（带符号） | |
| `dist_ratio(p, q, ref)` | 两点距离 / 参考长度 | 参考长度用躯干长（肩中点到髋中点）或肩宽，**不可用画面尺寸** |
| `symmetry_index(l, r)` | `2·\|l−r\| / (l+r)` | 作用于同尺度的左右同名量 |
| `midpoint(a, b)` | 两点中点 | 用于髋中点、肩中点 |
| `signed_offset(p, line)` | 点到直线的有符号距离 | 用于判断膝在髋踝连线内侧/外侧 |

### 2.2 特征清单

| 特征码 | 定义 | 主要用途 | 坐标依赖 |
|---|---|---|---|
| `knee_angle_L/R` | 髋-膝-踝 | 深蹲深度、跳绳缓冲、立定跳远落地 | 像素 |
| `elbow_angle_L/R` | 肩-肘-腕 | 俯卧撑、引体向上、平板支撑（肘撑偏离） | 像素 |
| `shoulder_angle_L/R` | 髋-肩-肘 | 开合跳（取两侧较小者，见下一行） | 像素 |
| `shoulder_angle_min` | `min(shoulder_angle_L, shoulder_angle_R)` | 开合跳「两只手臂都举到位了吗」（落后那只才是判据） | 像素 |
| `hip_angle_L/R` | 肩-髋-膝 | 深蹲辅助、坐姿 | 像素 |
| `trunk_lean` | 髋中点→肩中点与竖直方向夹角 | 深蹲、俯卧撑、平板支撑（身体放平了没有） | 像素 |
| `thigh_tilt_L/R` | 髋→膝与水平方向夹角 | 平行蹲判定（无世界坐标时的深度替代） | 像素 |
| `frontal_knee_angle_L/R` | 髋→膝 与 膝→踝 在图像平面的夹角（正视） | 膝内扣 | 像素 + 正视机位 |
| `body_line_angle` | 肩中点-髋中点-踝中点 | 俯卧撑、平板支撑、仰卧 | 像素 |
| `body_line_offset_ratio` | (髋中点 y − 髋在肩踝连线上的投影 y) / 躯干长 | 俯卧撑塌腰/撅臀、仰卧起坐顶髋、平板支撑塌腰/拱起 | 像素 + 侧视机位 |
| `shoulder_height_ratio` | (踝中点 y − 肩中点 y) / 躯干长 | 仰卧起坐「肩胛有没有贴到垫上」 | 像素 + 侧视机位 |
| `foot_ground_angle_L/R` | 踝-脚跟 与 踝-脚尖 夹角 | 脚跟离地 | 像素 + 侧视机位 |
| `heel_rise_ratio_L/R` | (脚跟 y − 脚尖 y) / 足长 | 脚跟离地降级方案 | 像素 + 侧视 |
| `elbow_knee_ratio` | 肘点-膝点距离 / 大腿长 | 仰卧起坐触膝（**未实现，见下**） | 像素 |
| `wrist_ear_ratio` | 腕点-耳点距离 / 头宽 | 仰卧起坐抱头（**未实现，见下**） | 像素 |
| `mouth_wrist_dy` | (嘴中点 y − 腕中点 y) / 躯干长 | 引体向上过杠 | 像素 |
| `hip_height_ratio` | (髋中点 y − 膝中点 y) / 躯干长 | 下蹲深度降级方案 | 像素 |
| `ankle_y_amplitude` | 踝点 y 相对站立基线的峰谷差 / 躯干长 | 跳绳、开合跳节奏 | 像素 |
| `leg_spread_ratio` | \|左踝 x − 右踝 x\| / 肩宽 | 开合跳「开得够不够」 | 像素 + **正视机位** |
| `pelvis_offset_ratio` | (髋中点 x − 两踝中点 x) / 肩宽 | 重心偏移 | 像素 |
| `foot_height_ratio` | (画面高度 − 两脚尖中点 y) / 躯干长 | 跳绳「离没离地」 | 像素 + **画面下缘当零点** |
| `foot_gap_ratio` | \|左脚尖 y − 右脚尖 y\| / 躯干长 | 跳绳「单脚落地」 | 像素 |
| `phase_duration_ms` | 各相位时长 | 节奏评价 | 时间域 |

`body_line_angle` 与 `body_line_offset_ratio` **不是同一个量的两种写法，不能互相
顶替**：前者是 `angle3` 的夹角、值域 [0°, 180°]，髋往上顶和髋往下掉都只是让它
变小，两种错在它上面**逐位相同**（`pu_test.dart` 里有一条断言量了这件事）；
后者带符号（正 = 髋更低 = 塌腰，负 = 髋更高 = 撅臀），参照系取的是重力方向
（图像 y 轴）而不是「连线的哪一侧」—— 后者会随人面朝画面哪一边翻号，
同一个塌腰在两个站位上会得到一正一负。俯卧撑的 `PU_HIP_SAG` 与 `PU_HIP_PIKE`
共用它、方向相反，这是这两条规则能被分开的唯一原因。

`shoulder_height_ratio` 与 `body_line_offset_ratio` 是同一个几何问题的两个问法：
前者问「肩比踝高多少」（肩胛贴没贴到垫），后者问「髋在这条连线的哪一侧」
（臀有没有离垫）。仰卧起坐两条判定各用一条，缺一个就有一条问不出来。
**注意它的量纲**：臀贴在垫上时它等于 `cos(躯干与竖直的夹角)`，**上界是 1** ——
那个上界只在「躯干严格竖直」一个奇点上取到，所以合格线不能取 1.0
（`situp.dart` 文件头推了一遍，`TrackingConfig.situpSeatRatio` 取 0.75）。

`foot_height_ratio` 与 `foot_gap_ratio` 是跳绳的两个量，**共用「脚尖」这个参照点，
但是否共用画面零点正好相反**，这个区别不能含糊：前者拿画面下缘当零点，
所以它的**绝对值由机位高低决定**（手机架在腰高还是胸口高，同一个站姿读数能差
一大截），只能在同一组内比 —— 也正因如此，跳绳那三条分段线全部记成
**相对本人站立基线的增量**，而「手机架稳不动」是这个量成立的前提（画面下缘得是
一个固定不动的水平面），`rope.dart` 文件头推了一遍。后者是**差分**，
零点在相减时约掉了，所以它跨组、跨机位可比，三条判定里只有它不需要基线。
另外 `foot_gap_ratio` 取的是**绝对值**：跳绳时先落地的是哪只脚是随机的，
有符号量的分布是双峰的，一条阈值写不出来。

`mouth_wrist_dy` 是引体向上「下颌过杠」那条判定的输入，**它不是代理量，是一条
几何恒等式**：双手握在杠上，腕的高度**就是**杠的高度，所以 `嘴_y − 腕_y < 0`
与「下颌过杠」是同一件事，不是近似。它带符号（图像 y 轴向下），所以那条阈值
是个**负数** —— 改成「取绝对值再判」会把「挂在杠下」与「拉过头」压成同一个数，
而这条规则只有一句纠正建议。分母取躯干长，身高、镜头远近、体型在里面一起约掉，
所以它是绝对阈值、不挂本人基线。它**没有机位门控**（45° 与正视下都算得出），
但它有一个别人没有的性质：**它是全项目唯一一条判定用嘴点的特征**，而嘴是 33 个点
里可见性最低的几个之一 —— 于是 `PULLUP_CHIN_NOT_OVER` 成了全项目唯一一条
**会因为遮挡而改变结论**的判定，窗口必须切在顶点段（见 §4.3）。

**这张表是 M1 的规格，不等于当前已经实现的特征。** 现在两侧（`features.py` /
`features.dart`）实装的是 31 个，与本表的出入有两类，写在这里免得下一份统计
再对不上：表里 `foot_ground_angle_L/R`、`elbow_knee_ratio`、`wrist_ear_ratio`、
`ankle_y_amplitude`、`phase_duration_ms` **还没有实装**；
代码里另有 `frontal_knee_offset_L/R`、`knee_symmetry`、`frontal_knee_angle_max`
三个已经实装、本表没列的（前两个是深蹲、第三个是开合跳用的 —— 顺带一句，
它同时也是深蹲 `KNEE_VALGUS` 用的特征，而深蹲跑 45°，所以那条判定在产品里
**一帧都没执行过**，见 §5.2）。
`elbow_knee_ratio` 与 `wrist_ear_ratio` 这两个尤其要留意：它们当初是为仰卧起坐的
「肘触膝」「双手抱头」设计的，而那两个量在单目下**不成立**（都是接触关系，
2D 点距分不出「贴着」与「一臂之遥」，见 `server/app/taxonomy.py` 里那两条的注记）
—— 所以它们不该被「补上」，该从这张表里去掉，只是本轮不动第 2 节。

每个特征在代码中必须同时携带：`value`、`unit`、`coord_space`、`valid`（bool）、`invalid_reason`。

## 3. 滤波与防抖

### 3.1 三级流水线

```
原始关键点 → [L1 坐标级] → [L2 信号级] → [L3 状态级] → 稳定输出
```

| 级别 | 方法 | 参数（工程默认，见 §7.1） | 作用 |
|---|---|---|---|
| L1 坐标级 | 3 点中值滤波 → One Euro 滤波 | 逐点逐轴独立 | 去尖峰 + 抑制抖动，低速强平滑、高速低延迟 |
| L2 信号级 | One Euro 滤波 | 作用于角度序列 | 同上，但保留有意的小幅动作 |
| L3 状态级 | 滞回阈值 + 最短停留 + N-of-M 投票 | 见 §4.1 | 消灭边界抖动导致的重复计数 |

**为什么不用卡尔曼**：参数难调、工程量大，收益局限于锚点信号。仅在跳绳等周期性计数场景考虑对单一标量（踝点 y）使用。

**为什么不只用均值滤波**：延迟大且拖尾，会抹掉深蹲底部和顶部的关键极值点。

### 3.2 关键点丢失的处理

| 情形 | 处理 | 约束 |
|---|---|---|
| 单点可见性 < 阈值 | 依赖该点的特征输出 `null` | 该帧不参与判定 |
| 短时丢失（< 阈值） | 线性插值**仅供显示** | **插值帧不参与计数与错误累计** |
| 一个 rep 的有效帧占比 < 阈值 | 该 rep 标记 `low_quality` | 只计数，不评错误，提示重做 |
| 长时丢失（> 阈值） | 终止当前 rep 进度（不计数），提示重新入镜 | 从校准态重新同步，无需重站 |
| 单帧跳变 > 阈值×躯干长 | 判为伪帧丢弃 | |

**"插值帧不参与判定"是硬约束**——否则会凭空造出不存在的动作数据，训练与评测全部污染。

## 4. 动作状态机

### 4.1 通用框架

所有动作共享同一套状态机骨架，动作差异全部封装在「动作定义」中，以注册表模式加载。**新增动作 = 新增定义文件，不改引擎。**

> **别把这里的动作定义与手机首页那份动作清单弄混。** `app/lib/ui/exercise_catalog.dart`
> 里那张表是一份**产品**清单：分组、图标、tagline、上没上线。它**不是**这里的动作
> 注册表，也不能当成交付范围的依据 —— 一个动作能不能做，取决于这一层有没有它的
> 定义文件（现在 `app/lib/domain/exercises/` 下有 `squat.dart`、`slj.dart`、`jj.dart`、
> `pu.dart`、`situp.dart`、`rope.dart`、`pullup.dart`、`plank.dart`、
> `sit_reach.dart` 九个）。
>
> **两张表现在正好都是 9 项，但那是巧合、不是同一件事。** 2026-10-06 之前它们差着一项：
> 坐位体前屈在产品清单里标着「未开放」，在这一层**没有任何定义**。**它们是对齐过，
> 但对齐的方式是补上定义文件、不是删掉卡片** —— 两张表下一次分叉时（新动作先立产品
> 形状、后补定义）方向依旧是这个。

**动作定义须声明：**

| 字段 | 说明 |
|---|---|
| `action_code` | 稳定英文编码，如 `SQUAT` |
| `required_landmarks` | 该动作必需的关键点索引集合 |
| `camera_view` | `frontal` / `sagittal` / `oblique45` |
| `feature_schema` | 本动作用到的特征及 schema |
| `states` / `transitions` | 状态与转移条件 |
| `rule_set` | 引用的错误规则编号 |

**转移条件的三层防抖（全部必加）：**

1. **滞回** `h` — 进入与退出的阈值不同，避免边界来回跳
2. **最短停留** `min_dwell_frames` — 新状态必须维持若干帧才确认
3. **N-of-M 投票** — M 帧中至少 N 帧满足才升迁

**rep 缓冲的记账规则（引擎级，与任何动作定义无关，2026-10-05 补齐）：**

- 一次 rep 从**离开 `resting_state` 的那一帧**开始，到**重新进入它的那一帧**封存；
  没有到过 `bottom_state` 的段落不计入 `rep_count`，而是计进 `discarded_reps`。
- 起点那一帧**同时**是「新状态的第一帧」，所以它在那一帧上发生的转移也必须
  参与记账。原先的等待期分支只把它收进缓冲区（那条「不保留历史」管的是内存，
  不管记账），**漏掉了「这一帧已经到过 `bottom_state`」这一笔**。
- **漏掉的后果是静默毁掉一整类动作定义**：`resting_state` 的下一步就是
  `bottom_state` 的那一类 —— 跳绳的 `GROUND → AIR`（`AIR` 就是 `bottomState`）
  正好落在 rep 起点这一帧上，于是每一次 `_seal` 都走「没到过底部」的分支，
  **整组一次都不计数、全部计进 `discarded_reps`**，而 HUD 上的状态词一路都是对的，
  屏幕上什么错都不报。
- **它为什么在跳绳之前没暴露**：其余动作的 `resting_state → bottom_state` 都要
  先经过一个过渡态（站立 → 下降 → 最低点），那个进入转移不在 rep 起点那一帧上。
  `A ⇄ B`（B 是底部）这种形状是跳绳第一次出现。
- 两侧各有一条**与动作定义无关**的守卫测试（Dart 用同一形状的合成状态机、
  Python 见 `test_exercises.py::TestRepBufferBookkeeping`）：记账规则属于引擎，
  它的守卫不该寄生在某个动作的测试里。

**标定结果的拼装也要有守卫（同一天发现的第二处，`Calibrator`）：**
`Calibrator.feed` 是按 `required` 逐量累加样本的，而结果 `Calibration` 是
**手写**的一项一项拼出来的（它比 `required` 多两个总是要的膝角与躯干倾角，
其余每一项可空）。**采到 ≠ 放进去** —— 采样循环里采了、拼装时漏了的表现极隐蔽：
标定照样走完、`isReady` 为真、屏幕上一切正常，而**读那一项的人**在别处抛。
2026-10-05 就是这样漏掉跳绳要的 `footHeight` 的，抛点在会话建 runner 的那一刻，
也就是用户做完一组、标定刚结束的时候 —— 一组白做。守卫的判据是
「声明要采的每一个量，从标定结果里都读得回」，两侧各有一条
（Dart 遍历 `kActionSpecs`、Python 遍历 `Calibrator.required`）。

### 4.2 深蹲（Phase 1 首个动作）

**机位**：侧视为主（判深度、躯干前倾、脚跟离地），正视为辅（判膝内扣、左右对称）。

**状态**：

```
CALIBRATION → STANDING ⇄ DESCENT ⇄ BOTTOM ⇄ ASCENT → STANDING
```

| 状态 | 含义 | 进入条件 |
|---|---|---|
| `CALIBRATION` | 采集站立基线：站立膝角、躯干角、脚跟基线 | 启动或长时丢失后 |
| `STANDING` | 站直待发 | 膝角 > 站立基线 − 滞回 |
| `DESCENT` | 下降中 | 膝角持续下降且低于站立基线 − 滞回 |
| `BOTTOM` | 最低点 | 膝角 ≤ 深度线，或出现局部极小后连续回升 |
| `ASCENT` | 上升中 | 膝角回升且 > 深度线 + 滞回 |
| → `STANDING` | **一次 rep 完成** | 膝角 > 站立基线 |

**rep 封存**：每次回到 `STANDING` 时，把从上一个 `STANDING` 到本次的全部帧特征打包为一个 rep 记录，含各相位时长、最低点窗口内各特征值、触发的错误列表。

**待核定**：深度线（合格深蹲的膝角切点）、滞回量。见 §7.3。

### 4.3 其余动作要点

**立定跳远要点**（实现见 `app/lib/domain/exercises/slj.dart`、`domain/src/vitalteen_domain/exercises/slj.py`）：

- **机位必须斜前 45°，不是可选项。** 它的 `heel_rise_ratio_L` 与深蹲同款声明
  `views: [sagittal, oblique45]`；正视机位下 `Calibrator.feed` 永远拿不到第五个
  必需特征，表现是标定条卡住不动、**不报任何错**。守卫这一点的不是注释，
  是首页的站位门禁（`slj_session_test.dart` 有一组测试钉住它）。
- **没有 `LAUNCH → LAND` 这条边**，这是有意的。守卫 `bool Function(Signals)`
  看不见时间戳，而 LAUNCH 的进入线（`stand − minBendDeg + 滞回`=158）低于落地线
  （`stand − landingFlexDeg`=163），于是「已进 LAUNCH 且当前膝角低于落地线」
  在进入的那一帧就恒真 —— 那条边会在半空中直接触发。代价是**没蹬到近乎伸直的
  一跳不被计数**（停在 LAUNCH/FLIGHT 直到超时丢弃）。这是朝着安全方向的损失：
  少计一次，而不是凭空多出一次。旋钮是 `flightExtensionDeg`。
- **人会出画，这是常态。** 手机架在两米外，一次立定跳远前进一米多，出画那一瞬间
  多半正好是蹬伸最快的那几帧 —— 而「蹬直」这条线相对站立只差 4°，于是状态机
  停在 `LAUNCH`。人回来蹲下时，这一步被读成**回蹲**（`LAUNCH → PREP`），站直又把它
  推回 `FLIGHT`，最后等超时丢弃：**一次真跳连同一次本来看得见的落地一起没了**。
  修法是 `ActionDefinition.lossRecovery`（`{LAUNCH: FLIGHT}`，两侧同名）：
  长丢失结束后先按它重同步，把「蹬伸那几帧没看见」当成「人已经离地」。
  **只登记这一条，刻意不登记 `LAUNCH → LAND`** —— 后者会封存一次落地没被看见的
  rep，拿人走回来的那几帧去评落地缓冲，那是编分数；而现在落地**仍然要靠看得见的
  蹲下来认定**。重同步只在丢失超过 `interruptionThresholdMs`（1.5 s）后发生，
  否则「假跳中间掉一帧」会被改判成一次落地，凭空多出一次。
- **`FLIGHT → LAND` 的髋高门槛**（`landingHipFloor`）。收腹举腿是立定跳远的
  正规技术，腾空中膝会折到胸口、`hip_height_ratio` 转负；不挡的话状态机在
  半空就判落地，而「落地缓冲」判的是 LAND 相位上膝角的最小值 ——
  于是**收腿越标准越被判成缓冲充足**，那是一条永远不再触发的规则。
- **五条规则**：`SLJ_PREJUMP_HEEL_OFF` / `SLJ_TAKEOFF_ASYNC` /
  `SLJ_LAND_ASYNC` / `SLJ_LAND_STIFF` / `SLJ_TRUNK_CONTROL`。其中两条
  「双脚不同步」用的是 `knee_symmetry` 这个**代理量**，不是足底接触测量
  （单目视频没有足底接触信息，也无从确认真正的离地时刻）；且因为
  `extended` 读的是两膝**均值**，两腿差得越大越够不到腾空线，那一跳会**不被
  计数**而不是被判为不同步 —— 所以这两条抓的是中等幅度的不同步。
- **测不出距离。** 单目无世界坐标（附录 A），卡片上那句「只判动作规范性，
  测不出厘米成绩」在上线后**照留**。

**开合跳要点**（实现见 `app/lib/domain/exercises/jj.dart`、
`domain/src/vitalteen_domain/exercises/jj.py`）：

- **机位只能是正面，而代价落在标定上。** 判「落地膝内扣」的
  `frontal_knee_angle_max` 与判「开得够不够」的 `leg_spread_ratio` 都声明
  `views: [frontal]`，45° 下它们是 `view_mismatch`，两条判定**静默消失**。
  但正面机位下 `heel_rise_ratio_L`（声明 `[sagittal, oblique45]`）恒不可用，
  而 `Calibrator.feed` 原先硬性要求它 —— 于是标定条卡在 0、**不报任何错**、
  永远进不了计数。所以这一轮动了共享组件：标定要求的基线量从写死的四个特征
  变成**随动作而变**（`ActionSpec.calibrationBaselines`，默认仍是原来那三个），
  开合跳的集合是 `{膝角, 躯干倾角, 分腿比}`。顺带同源的还有两处
  「把深蹲要什么当成所有人都要什么」：站位门禁的极性（`requiresFrontal`）
  与必需关键点集（`requiredLandmarks`，开合跳不要把左脚跟/左脚尖留在名单里
  —— 否则左脚一出画就被拦住，理由还是「脚跟离地判定做不了」，
  一件这个动作根本不做的事）。
- **四条分段线全部相对本人站立基线，三条判定全部用绝对阈值。** 分腿比已用
  肩宽归一（体型与镜头远近在算式里约掉），肩角是夹角（臂长约掉），
  `frontal_knee_angle` 也是夹角 —— 这几个量本来就不需要个体化。
  **尤其不能给 `jj.spread_min_ratio` 挂基线偏移**：并腿站立时两踝横向间距接近 0，
  「基线 × k」也接近 0，而判据是「峰值 < 阈值」，阈值恒接近 0 而峰值恒大于 0,
  这条规则于是**永远不触发**且不报错。
- **两条「幅度不足」类规则跑在 `Phase.ALL` 上，不是切到顶点。** 理由与直觉相反：
  把窗口切到一个只在「已经开到位」时才存在的状态上，恰好会让这条规则**在最需要
  它的人身上失明**；而「整次动作的峰值」在整段上取 `max` 与在顶点段取 `max`
  是同一个数。这也是 1.4 节那条「相位只映射 `CLOSING`」的另一面。
- **`Phase.contact` 是新加的成员，刻意不复用 `landing`。** 后者的语义是
  「触地之后的屈曲缓冲」（它判这一段上膝角的最小值），而开合跳判的是
  「脚落下来时膝盖朝哪边」—— 一段是缓冲深度、一段是额状面的朝向。
  合成一个成员会让下一个人以为两条规则在问同一个问题。
- **三个错误码**：`JJ_INSUFFICIENT_SPREAD`（**新增**，原来是预登记五码里没有的
  —— 卡片承诺「看开合到不到位」，而原来那五个里没有一个管分腿幅度）、
  `JJ_INSUFFICIENT_ARM`、`JJ_KNEE_VALGUS`。另外两个（`JJ_LAND_STIFF`、
  `JJ_DRIFT`）**在这一机位下没有可信的量**，不是没排期：正面画面上膝盖的屈伸
  几乎不改变投影角度（与 §4.2 为深蹲写的同一个现象），而「前后漂移」的方向
  在正面就是镜头方向本身。`JJ_ARM_ASYNC` 要第三个新特征（两侧肩角之差），
  卡片没有承诺它。三个都继续留在 `server/app/taxonomy.py` 里不实现 ——
  那张表的文件头已经承认过这种状态。

> **顺带记下的一件事：深蹲的 `KNEE_VALGUS` 在产品里一帧都没执行过。**
> 它用的就是 `frontal_knee_angle_max`，而该特征声明 `[frontal]`、深蹲跑的是
> 45° —— 于是它每次都在「特征不可用」上跳过。**开合跳是这条判定第一次真正
> 跑起来**（见 §5.2 那条学术保留，它同样适用于开合跳这一条）。
> 下一个人多半会以为深蹲那条在工作。

**俯卧撑要点**（实现见 `app/lib/domain/exercises/pu.dart`、
`domain/src/vitalteen_domain/exercises/pu.py`）：

- **回到 45° 主链路，代价换了一种。** 开合跳那三处共享组件改动（基线集、
  门禁极性、必需关键点）它一处都不需要 —— 但门禁还有第四处「把深蹲要什么
  当成所有人都要什么」：判「离得远不远」用的是**纵向**跨度、两个阈值也是按
  身高标定的，而趴着的人纵向只剩身体的厚度。不处理的话，一个距离站得完全
  正确的人在整组里都会看到一条**拦人级**的「离得有点远（身高只占画面 10%）」。
  于是那个判据改成取纵向与横向里**较大的那个**跨度 —— 对直立的人 `max` 取到的
  就是纵向，所以三个既有动作**零行为变化**（`camera_position_check_test.dart`
  有一组守卫钉住这件事）。**分叉的原型 `ActionSpec.isLyingDown` 已经删掉**
  （2026-10-06）：横屏之后转正图宽大于高，按姿势分叉两种情形都会误报，
  而门禁这一层拿不到姿势，分叉只能靠调用方传进来的常量，错了没有任何东西会报。
  **那两个阈值对趴着的姿势是未标定的**，与 `frontalRatio` 同一种状态。
- **四条判定一条基线都不挂，标定只采框架强制要求的两项。**
  `ActionSpec.calibrationBaselines` 收到 `BaselineKey.alwaysRequired`
  （膝角、躯干倾角）—— 多采一个没人读的脚跟抬升（45° 下采得到）会让
  必需关键点名单里多出脚跟与脚尖，而后果是趴下之后左脚一出画就被拦住。
  标定对俯卧撑是**走过场**（会话的状态机要求标定完才建定义），但那 15 帧躲不掉。
- **`TOP` 是计数门槛，「下得够不够深」是另一条线。** `pushupDepthDeg`（100°）
  以下才进 `BOTTOM`，进不去的那次走 `discardedReps`；而
  `PU_INSUFFICIENT_DEPTH` 判的是进来的那些里肘角**峰值**高于 90° 的。
  合成一条的话，用户就分不清「这一次没算」与「这一次算了但可以更好」——
  同开合跳 `OPEN` 与 `JJ_INSUFFICIENT_SPREAD` 的关系。
  顶部那条同理：`pushupTopDeg`（165°）是分段线，
  `PU_INCOMPLETE_EXTENSION` 判的是 165°–170° 那一段。
- **`PU_HIP_SAG` 与 `PU_HIP_PIKE` 共用 `body_line_offset_ratio`、方向相反**，
  一个 `above` 一个 `below`。写反任何一条的表现是「这两条判定怎么老是乱报」，
  而两条要说的纠正建议正好相反 —— 所以测试里必须**成对断言**
  （违规命中 + 合规不命中 + 两条不互相顶替）。
- **四条判定都跑在 `Phase.ALL` 上。** 问的都是「整次动作的极值」，
  在整段上取 `reduce` 得到的与切到某个相位是同义的，而 `TOP` 本来也不该映射
  相位（rep 缓冲从离开它开始）。所以它们**显式写 `ALL`**，而不是写一个
  没被映射的相位然后靠 `RepWindow.select` 的整段回退兜住行为 ——
  那样行为一样、测试不会红，但意图丢了。
- **两个错误码测不出来**，原因各不相同：`PU_ELBOW_FLARE`（肘外展）要的是
  上臂相对躯干在**额状面**内张开的角度，而侧视/45° 画面上「手臂往前摆」与
  「往两侧张」投影同形 —— 卡片上那半句承诺据此收掉了；`PU_HEAD_ALIGN` 要一个
  还不存在的特征，且 §7.3 第 3 条把它列在待核定里。`PU_TEMPO` 要的是组内跨次的
  时长分布，那是**会话级**的量，不是单次判定。三个都留在 `taxonomy.py` 里不实现。

**仰卧起坐要点**（实现见 `app/lib/domain/exercises/situp.dart`、
`domain/src/vitalteen_domain/exercises/situp.py`）：

- **计数点是「回到 `SEATED`」，不是本表原稿写的「回到 `LYING`」。** 原稿写的是
  `LYING` + 肩胛触垫确认，**做不出来**：`RepTracker` 的缓冲从**离开** restingState
  那一帧开始、到重新进入它时封存，restingState 本身不出现在已封存的 rep 里。
  把 `LYING` 当 restingState，「这次肩到底贴到垫上没有」那个证据就正好落在缓冲的
  边界上，而且**偏向起得快的人** —— 防抖让封存晚几帧，起得越快、封存时肩已经多降了
  一截，读数越小越不容易被判「没贴垫」，而慢速控制恰恰是这个动作最该鼓励的。
  换成 `restingState = SEATED`、`bottomState = LYING` 之后躺平那一段落进缓冲中段，
  `Phase.bottom` 上的最小值才恢复本来的意思。代价是启动时状态机停在 `SEATED`，
  HUD 上「坐起」那个词会闪一下（几十毫秒，等用户躺下就翻过去）。
- **「坐起线」取不到 1.0，因为那是一个物理上界。** `shoulder_height_ratio` 是
  (踝中点 y − 肩中点 y) / 躯干长；臀贴在垫上时肩绕髋转，于是
  `比值 = cos(躯干与竖直的夹角)`，**上界恰好是 1**，而 1 只在「躯干严格竖直」
  那一个奇点上取到。国标的收势是前倾（肘触膝），前倾 30° 就只有 0.87 ——
  **取 1.0 会让标准动作永远不被计数，且什么错都不报**。更坏的是它会奖励正要被罚的
  那个错：臀一离垫肩被顶高，比值能越过 1.0，老老实实做的人够不着线、顶着髋借力的
  人够得着。所以 `situpSeatRatio` 取 0.75。**这条不是阈值治理的事** ——
  它判的是「算不算一次」，属 §7.1 的工程参数，与深蹲的 `minBend` 同类。
- **三条判定各看一件事，而且三条都是绝对阈值**（`thresholdOffsets` 为空）：
  `SU_SHOULDER_NOT_GROUND` 看 `shoulder_height_ratio` 在**最低点**的最小值、
  `SU_HIP_LIFT` 看带符号的 `body_line_offset_ratio` 在**整段**上的最小值、
  `SU_KNEE_ANGLE` 看 `knee_angle_L` 在整段上的最大值。三个量要么已用躯干长归一、
  要么本来就是夹角 —— 体型在里面约掉了，再乘一个本人基线只会引入噪声。
- **顶髋那条跑在 `Phase.ALL` 上，不能切成最低点。** 坐起途中髋自然高于肩-踝连线
  （合成帧上量到 > 0.10），切到最低点就会把那一段当成顶点，而这条规则叫
  「臀离垫借力」，报出来的是另一件事。两侧各有一条断言钉住这件事。
- **两条判定在正视下静默消失。** `shoulder_height_ratio` 与
  `body_line_offset_ratio` 都声明 `[sagittal, oblique45]`，正视下身体的**长边就是
  镜头方向本身**。所以站位与深蹲同向（要侧身），`advisoryAdvice` 刻意留空 ——
  仰卧起坐没有「提示级」那一档，侧对与 45° 都放行、正对拦住。
- **起始姿势必须躺着，这是这一轮唯一一处「不绕开就走不通」。** 门禁判「离得远不远」
  的 `tooFarBelow`（0.45）是按**站姿**标定的（`camera_position_check.dart` 自己写了
  「这两个数是按直立的人标定的」），而仰卧起坐的起始姿势是这一组里最显小的：同一个人、
  同一部手机，合成帧上躺下占画幅 45.1%、坐着只剩 26.2%。这一条**拦人**，而相机页的
  自动倒计时以「门禁放行」为条件 —— 过不去就永远不进标定，用户看到的是「离得有点远，
  请靠近一些」，照做之后一躺下又变成「身体贴到画面边上」。现在的办法是让用户
  **躺着开始**（`ActionSpec.framingHint` 里那句话的全部意思），`su_session_test.dart`
  里有一条**记账断言**把「坐姿被拦」钉住 —— 它钉的是这个事实本身，不是「判据没被动过」：
  判据在 2026-10-06 为横屏改成「取两个跨度的 max」之后，坐姿仍被拦（它的高仍大于宽，
  max 取到的还是高），所以那条断言照样绿。**给坐姿定真数要真机数据**，
  在那之前不要凭推算改 `tooFarBelow`。
- **两个错误码测不出来**：`SU_HANDS_OFF_HEAD`（双手抱头）与
  `SU_ELBOW_NOT_TOUCH_KNEE`（肘触膝）判的都是**接触关系**，而 2D 关键点之间的距离
  在透视下分不出「贴着」与「一臂之遥」，所以 §2.2 表里为它们预留的
  `wrist_ear_ratio` / `elbow_knee_ratio` 两个特征也**不该被补上**。两个码继续留在
  `taxonomy.py` 里不实现。

**跳绳要点**（实现见 `app/lib/domain/exercises/rope.dart`、
`domain/src/vitalteen_domain/exercises/rope.py`）：

- **机位是 45° 主链路，理由是硬的。** `foot_height_ratio` 与 `foot_gap_ratio` 都声明
  `views: [sagittal, oblique45]`，正视下它们是 `view_mismatch` —— **分段信号整段
  不可用**，机器永远停在 `GROUND`，一次都数不上，而屏幕上不报任何错
  （同类失效见本节立定跳远与开合跳两条）。
- **`foot_height_ratio` 是全仓库唯一一个拿画面当零点的量。** 别的动作都刻意避开
  这个做法（画面上下的位移一半来自人自己的移动），它能这么做只因为跳绳有一条
  别人没有的前提：**手机架稳不动**，于是画面下缘是一个固定不动的水平面。
  代价是这个量的**绝对值由机位高低决定**，所以三条分段线全部记成相对本人站立基线的
  增量（`footHeight` 基线），而**标定时必须站稳在地上** —— 这是唯一一个
  「基线本身就代表接触地面」的动作。`framingHint` 那句「把手机架稳别动」
  不是语气问题，是判据本身的要求。
- **三态环，第三个状态 `CUSHION` 是为了把证据塞进窗口里。** `GROUND ⇄ AIR`
  两态**看起来**够用，但 rep 缓冲是「离开 restingState 那一帧开始、重新进入它的
  那一帧封存」—— 两态下封存发生在**脚尖刚碰到地面的那一帧**，而落地缓冲
  （膝屈再伸的那一下）全部发生在之后：`ROPE_LOW_BUFFER` 要判的证据整个落在 rep
  窗口之外，规则照常出结论、说的却是另一件事。所以触地只进 `CUSHION`，
  `CUSHION → GROUND` 的守卫是「脚尖贴回地面 **且** 膝角回到站立线」
  （与立定跳远的 `LAND → STANDING` 同形）。**这不是为跳绳特设的机制**：
  `pu.dart` 的 `TOP`、`situp.dart` 的 `SEATED` 都在解决同一件事。顺带得到一条可推理的
  不变式：既然封存要求膝角曾回到站立线，那么**每一个封存下来的 rep，膝角一定回到过
  站立线** —— `ROPE_LOW_BUFFER` 与这条分段线的相对关系就是建立在这上面的
  （阈值表里那条 `_note`）。
- **`restingState` 的下一步就是 `bottomState`（`GROUND → AIR`），这是全项目第一次
  出现这种形状**，也正是本轮修掉的那个引擎 bug 的触发条件 —— 见 §4.1 的 rep 缓冲记账。
- **相位映射是空表**，三条规则全部跑在 `Phase.ALL` 上。不映射 `CUSHION` 是有意的：
  落地缓冲只有 2–5 帧，拿它当相位窗口会让「膝屈得最深的那一帧」大概率落在窗口外，
  而 `RepWindow.select` 对没有区间的相位**退化为整段** —— 一条静默的误判路径。
  整段上取膝角最小值本来就能回答「这一跳屈没屈膝」：腾空时腿是伸直的，屈膝只发生在
  触地那一下，两个窗口在**本动作里**是同一个数。
- **防抖那一组数（`voteWindow` / `voteRequired` / `minDwellFrames` = 2 / 2 / 1）
  是节奏逼出来的，不是口味。** 状态机每次转移都清空投票历史，每个状态都要在状态内
  重新凑满票，三态环最短 `3 × voteWindow` 帧；20 fps 下 6 帧是 0.3 秒一次
  （合 200 次/分），在学生 1 分钟跳绳的 100–180 次/分之上留了余量。默认那一组
  （5/4 + 3）是每状态 5 帧、一轮 15 帧 = 0.75 秒一次（80 次/分），
  **会把跳绳数成一半**，而界面上一切正常。代价是一轮只有 2 帧防抖；
  **真机上万一多计，先调 `voteWindow`，不要去调那三条分段线。**
- **三条规则**：`ROPE_LOW_BUFFER`（`knee_angle_L` 整段最小值、`Reduce.min`、
  `Direction.above`）、`ROPE_TRUNK_LEAN`（`trunk_lean` 整段最大绝对值，
  相对本人站立基线）、`ROPE_SINGLE_LEG`（`foot_gap_ratio` 整段最大值，绝对阈值）。
  三条都取极值再比线，不是逐帧计数 —— 一次十来帧，帧计数会把过渡帧全算进去。
  `ROPE_SINGLE_LEG` 刻意不挂基线：站定的人左右脚尖本就等高，「基线 × k」也是
  ≈ 0，而线在 0 附近时每一次落地都会命中。
- **两个码测不出来，不是没排期。** `ROPE_ALTERNATING`（交替跳）判的是
  「组内这几跳是不是左右换着落脚」—— 一个跨次的时间序列模式，而规则引擎对每一次
  动作独立求值（窗口只有十来帧），没有「上一跳落在哪只脚上」这个输入；
  `ROPE_DRIFT`（位置漂移）要的是前后位移，而「前后」在 45° 机位里几乎就是镜头
  方向本身 —— 单目无世界坐标时量不出来，而「手机架稳不动」这个前提又拿掉了唯一
  能替代世界坐标的参照。两个码继续留在 `taxonomy.py` 里不实现。

**引体向上要点**（实现见 `app/lib/domain/exercises/pullup.dart`、
`domain/src/vitalteen_domain/exercises/pullup.py`）：

- **机位回到 45° 主链路，但理由与前几个都不同，要说清楚。** 它三条判定的特征
  （`elbow_angle_*` / `mouth_wrist_dy` / `trunk_lean`）**一个机位门控都没有** ——
  正对镜头时它们照样算得出数。代价藏在语义里：`trunk_lean` 量的是躯干**在画面上**
  偏离竖直多少，而摆动借力是身体在**前后**荡；正对镜头时那个方向就是镜头方向本身，
  特征有值、只是不再表示荡没荡 —— `PULLUP_SWING` 于是**静默地变成一条永不触发的
  规则**。前几个动作是「量不出来」，这一次是「量出来的不是那件事」。
- **计数门槛取肘角，不取下颌过杠。** 国标认的是下颌过杠，而本项目也量得到它
  （见 §2.2 的 `mouth_wrist_dy`），但它**不参与计数**：嘴是 33 个点里可见性最低的
  几个之一，拿它当门槛的后果是「拉到位了但脸被挡住 → 这一次不算」。
  肘角是肩-肘-腕三点，同一次动作里稳定得多。口径仍是那一句
  **「少判一次是提示，少计一次是丢数据」**。
- **`Phase.apex` 是新加的相位成员，不能借 `bottom`。** 后者的名字、文档、
  以及三条已经跑在它上面的规则说的都是「最低点」，而引体向上的极端在最高处。
  **更要紧的是：`PULLUP_CHIN_NOT_OVER` 是全项目唯一一条会因为遮挡而改变结论的
  判定，窗口切错不会报错、只会让判定换个意思。** 切窗的理由：跑在整段上时，
  嘴只要在组里任何一帧看得见（比如悬垂时），`Reduce.min` 就会取到那个悬垂读数，
  于是脸被上臂挡住、其实拉得很到位的人会被判成「没拉上去」。
- **那份遮挡容错只是【部分】的，本节必须如实写下来。** 相位窗口的尾巴上有几帧
  其实属于**下一段**：状态机的换相要经过驻留与投票，确认滞后于特征值的变化，
  于是顶点窗口的末尾落在了已经开始的下放段上。所以只有当嘴从顶点段起
  **一路遮到下放段也读不到**时，这条规则才真的退回「不知道」；只遮顶点段的话，
  那几帧尾部的下放读数照样会被取到。准确的说法是「**永不比整段宽松，且在一部分
  遮挡下更严格（严格的方向是少报）**」，而不是「挡到脸就一定不报」。
  两侧的用例为此各有一对断言：遮挡后不触发，以及**同一批帧把窗口换回整段就必须
  触发** —— 后半条是决定性对照，它证明那份「不报」真的来自窗口。
  `Phase.apex` 的文档里同时记了这条泄漏对**每一个**相位成员都成立。
- **标定是在杠上做的，这是唯一一个这样的动作。** `calibrationBaselines` 收到
  `BaselineKey.alwaysRequired`（膝角、躯干倾角），三条判定一条基线都不挂。
  默认那三项里多出来的 `heel_rise_ratio` 在这里**按定义就是错的**：标定时这个人是
  挂在杠上的，采出来的「站立基线」不是站立姿势下的数 —— 一个没人读、含义还是错的
  量比少采一个更糟。标定要求人在杠上稳住 15 帧，直臂悬垂本来就是稳的。
- **必需点名单里最不能漏的是双腕**，而**门禁拦不住这件事**。手看不见时
  `elbow_angle_*` 算不出来，状态机永远停在 `HANG`：一次都数不上、屏幕上不报任何错。
  门禁的缺失判据只有「躯干 / 腿 / 左脚」三组，手腕不在里面 —— 这是一条**记下来的
  边界**（`pullup_session_test.dart` 里有一条断言把它钉住），产品上靠
  `framingHint`（「把手机架到能同时看见横杆和双脚」）与 `PoseQualityTracker` 的
  覆盖率（用的是同一份名单）兜着。
- **`PULLUP_NOT_DEAD_HANG` 的阈值必须高于分段线。** 封存一次引体向上的前提是
  「肘角回到 `pullupHangDeg` 之上」，所以每个被计数的 rep 其整段最大值必然高于它；
  阈值定在它之下的话「最大值越界」恒假 —— 规则**永远不触发、也不报错**，
  看起来就像「没有人犯这个错」（同开合跳 `jj.spread_min_ratio` 那条陷阱）。
- **三条都取极值再比线，三条都是绝对阈值**：`PULLUP_NOT_DEAD_HANG`
  （`elbow_angle_L` 整段最大值、`Direction.below`）、`PULLUP_CHIN_NOT_OVER`
  （`mouth_wrist_dy` 顶点段最小值、`Direction.above`，**阈值是负数**）、
  `PULLUP_SWING`（`trunk_lean` 整段最大绝对值、`Direction.above`）。
  一个基线都不挂：肘角与倾角是关节角/绝对角，嘴高差已用躯干长归一。
- **两个错误码测不出来，原因不同**：`PULLUP_REST_TIMEOUT`（组内停顿超时）
  判的是**跨次**的时间间隔，而规则引擎对每一次动作独立求值（窗口只有一次拉起的
  几十帧），与跳绳的 `ROPE_ALTERNATING` 同属组级计时；腿的摆动与屈膝在 45°
  机位下与躯干的前后摆同形。两个都继续留在 `taxonomy.py` 里不实现。

**平板支撑要点**（实现见 `app/lib/domain/exercises/plank.dart`、
`domain/src/vitalteen_domain/exercises/plank.py`）：

- **计时制，全仓库第一个。** 一次 rep 是**一段连续支撑**：状态机在「离开
  `HOLD_BREAK`」那一帧开窗、在「回到它」那一帧封存，所以 rep 窗口就是那一段
  支撑本身。于是这个动作的两个产出正好是卡片承诺的那两件事 —— **每段撑了多久**
  （`RepWindow` 首末帧时间戳之差，早已进决策契约的 `duration_ms`）与**每段犯了
  什么错**（规则层），「累计撑了多久」是前者之和。**领域层为此一行都不用改**
  （rep 窗口本来就带时间戳），要改的是界面怎么显示：一段 40 秒的支撑被显示成
  「1 个」，用户会以为计数器没在看他。见 `ActionSpec.isTimed` 与
  `counting_hud.dart` 的计时分支。
- **两态环够用，而且不能再少一个。** 对照跳绳（它必须有第三个状态，因为要判的
  落地缓冲发生在「回到 restingState」**之后**）：平板支撑要判的东西全程都在支撑段
  里，窗口正好把它整个圈住。相位映射因此是**空表**，三条规则都跑在整段上 ——
  **别为了对称补一个 `Phase.bottom`**：那个成员的名字与写在它上面的三条规则说的
  都是「最低点」，而这里没有最低点，支撑段是一段时间。
- **分段门是三件事的合取，一条都不能省。** 身体放平（`|trunk_lean| ≥ plankLieDeg`）
  ＋ 体线大致成线（`|body_line_offset_ratio| ≤ plankLineEnterRatio`）＋ 撑地手臂在
  支撑带上（肘角落在 `plankElbowMinDeg..plankElbowMaxDeg`）。每条单拎出来都会把
  别的东西读成支撑：**站着的体线也直**（只看第 2 条，标定那 15 帧站立会被读成一次
  长支撑）、**趴在地上也直也水平**（只看第 1、2 条，中途趴下休息算「撑着」）。
  第 3 条是唯一能把「前臂支撑」与「站着/趴着」分开的量：前臂支撑时肘角被几何锁在
  90° 上下，而站着或放松趴着时手臂伸直（≈180°）。
- **门槛比判据宽，中间那一段就是规则有活干的地方。** 塌腰 0.20 判错、塌到 0.45
  才算「离开支撑位」；肘角同理。同开合跳的分腿幅度、俯卧撑的深度。
- **`_minViolatingFrames = 8`，比其余动作大得多（它们取 2）。** 两个原因都写在
  代码里：一是**计时制**，一段支撑动辄几百帧，抖一下不该在四十秒里变成一次犯规；
  二是**窗口的尾巴上有几帧不属于支撑段** —— 状态机换相要经过驻留与投票，确认
  「离开支撑位」的那一帧已经晚了几帧，而那几帧落在窗口里，取 2 会让**每一次正常
  收势都被判成塌腰**（收势正好从这几帧开始）。这与引体向上那条「相位窗口的边界
  不精确」是同一件事的两个后果。
- **两条阈值必须严格落在支撑带里面**（`plank.elbow_angle_min/max` 严格在
  `plankElbowMinDeg..plankElbowMaxDeg` 之内），否则每一个被计数的 rep 都够不着
  那条线，`PLANK_ELBOW` **永远攒不够 8 帧、一次都不触发、也不报错** ——
  看起来就像「没有人犯这个错」。同引体向上与开合跳那两条陷阱。
- **`PLANK_ELBOW` 一个码两条规则**（撑得太直、撑得太塌），这是**引擎明确支持**的
  做法（`RuleEngine` 按错误码去重），不要在实现里拆成两个码 —— 那会让出现率翻倍。
- **它挡不住什么（必须写进产品文案，这是附录 A 那一条的实例）**：一个**趴在地上**
  的人摆出同样的关节构型（前臂撑在身侧、肘角 90°、身体成一条线），在单目投影下
  与真正的平板支撑**完全同形** —— 两者的差别只有「离地多高」，而单目无深度参照。
  这是**能力边界，不是没排期**。缓解只有两条、都不是判定：站位门禁要求全身入画，
  以及计数屏上那个状态词（用户看得见系统把它读成了什么）。
- **`PLANK_HEAD`（头颈位置）不做，因为它要一个还不存在的特征** —— 耳（或眼）
  相对躯干长轴的偏角。现成的 `trunk_lean` 与 `body_line_offset_ratio` 都只用
  肩/髋/踝，头怎么摆完全不进这两个数。

**坐位体前屈要点**（实现见 `app/lib/domain/exercises/sit_reach.dart`、
`domain/src/vitalteen_domain/exercises/sit_reach.py`）：

- **状态环与仰卧起坐同形，但分段那个量的方向正好相反。** 那边量
  `shoulder_height_ratio`（**越大越躺平**），这边量 `hip_angle_L`（肩—髋—膝的夹角：
  坐直 ≈ 90°、前伸到底 ≈ 30–50°，**越小越前折**）。三条分段线
  （`sitReachUprightDeg` 75° / `sitReachHoldingDeg` 55° / `sitReachHysteresisDeg` 8°）
  的比较方向因此与 `situp.py` 那一份逐条反向。照抄仰卧起坐的写法不会报错 ——
  状态机照样「跑得动」，只是计数变成「折得越浅越算一次」。这三个数是**工程默认值**
  （判的是「算不算一次」），留在 `TrackingConfig` 里，不进 §7.3 那张表。
- **计数点是 `SIT_UPRIGHT`，不是 `HOLDING`**（`restingState` 与 `bottomState` 必须
  不同）。理由与仰卧起坐逐字相同：rep 缓冲从**离开** restingState 那一帧开始、回到
  它时封存，「这一次有没有真的前伸到底」这个证据落在中段才恢复它本来的意思。
  没伸到底的那些走 `discardedReps`，卡片上那句话是「没伸到底」。
- **两条规则，窗口不同而且必须不同。** `SRT_KNEE_BENT` 取 `Phase.BOTTOM`（前伸
  到底那一段 `knee_angle_L` 的最小值低于 `srt.knee_angle_min`）—— 前伸途中膝盖松
  一下不该判，屈膝只有在前伸到底那一刻才说明问题（膝盖一弯，上身够得更远）；
  `SRT_BALLISTIC` 取 `Phase.ALL`（`hip_angle_L` 的**掉头次数**高于
  `srt.ballistic_reversals_max`）—— 弹振发生在**前伸的过程中**，靠来回弹把人甩出去
  的人，前伸到底之后可以完全是静的。窗口写反的表现是同一件事：「这条判定时不时
  冒出来」，而看不出病因。
- **`Reduce` 新增第五个成员 `REVERSALS`**（窗口内相邻帧差分**符号翻转**的次数，
  带 `reversalDeadband`＝2° 的死区）。**这是本仓库第一次因为一个「错误的形态」
  而不是一个「量的缺失」去扩引擎。** 现有四个归约都只看得见一个点（挑一个代表值
  再比阈值），而弹振坏的正是整段序列的形状：靠来回弹够距离的人，前伸到底那个角度
  可以与慢慢伸的人**一模一样、甚至更远**，拿 `min(hip_angle_L)` 之类的量去判，
  两种人分不开。死区不能省 —— 匀速前伸叠上读数抖动会被数成上百次掉头
  （`rules_test.dart` 与 `test_rules.py` 里各有一条断言把它量出来）。
- **正对镜头是静默失败，而且特征层拦不住。** `hip_angle_L` 与 `knee_angle_L`
  **都没有 `views` 门控**：正视下它们照样有数（与仰卧起坐那两个带门控的量正相反）。
  可正对镜头时前折发生在**镜头方向本身**上，画面里的髋角几乎不变 —— 状态机永远
  停在 `SIT_UPRIGHT`、一次都数不上，而 HUD 一直显示「坐直」（那正好是实情的一半）。
  所以 45° 这件事只能靠 `blockingAdvice` 用话讲清楚，站位门禁那三层（机位/入镜/
  距离）里没有一层能替它把关 —— 这与深蹲「正对镜头计数恒为 0」是同一形状，
  但那次有特征门控兜着，这次没有。
- **标定是走过场，但那 15 帧躲不掉。** 两条判定一条基线都不用（髋角与膝角都是
  关节夹角，体型在它们里面约掉了），所以 `thresholdOffsets` 为空；而会话要求标定
  走完才建定义。标定时人**已经坐在垫上**（`framingHint` 说的就是这件事，
  与俯卧撑「先站着标定再趴下去」相反）。
- **它测不出什么。** 国标量的是**厘米**（指尖超过脚尖多少），端侧量不了 ——
  单目没有世界坐标（附录 A）。**「双手有没有并拢」这一轮也不做**：它要新增一个
  特征算子，而按工程约定，加特征 = 两侧实现 + 重生成
  `shared/fixtures/feature_conformance.json` + 两侧测试全绿；这个码继续留在
  `taxonomy.py` 里，理由写在那边。**横屏（`ActionSpec.requiresLandscape`）也不是
  为了量长度**，是让整个身体进得了画面（坐到垫上之后人是横着铺开的，
  竖直画面会把头与脚各切掉一端）。

## 5. 错误分类规则

### 5.1 命名规范

错误码格式：`<动作前缀>_<错误类型>`，全大写下划线。深蹲无前缀（`KNEE_VALGUS`），其余动作带前缀（`PU_HIP_SAG`、`PLANK_HIP_SAG`）。

每条规则必须声明：

| 字段 | 说明 |
|---|---|
| `code` | 错误码 |
| `name_zh` | 中文名 |
| `metric` | 依据的特征码 |
| `threshold_ref` | 引用的阈值表键（**不写死数值**） |
| `window` | 判定窗口（最低点窗口 / 中段 / 全程） |
| `temporal_rule` | 时序规则（持续帧数 / 组内出现比例） |
| `min_confidence` | 低于此置信度不产出该错误 |

### 5.2 深蹲错误规则（Phase 1 实现范围）

| 错误码 | 中文名 | 依据特征 | 判定窗口 | 易误判情形 |
|---|---|---|---|---|
| `KNEE_VALGUS` | 膝内扣 | `frontal_knee_angle_L/R` 取最大值 | 下降-最低点-上升 | 站距宽、天生胫骨外旋、斜拍透视压缩、长裤遮挡 |
| `INSUFFICIENT_DEPTH` | 下蹲深度不足 | `knee_angle` 极小值 | 全程 | 与"柔韧受限导致做不到位"混同——应附加柔韧提示而非判态度问题 |
| `EXCESSIVE_TRUNK_LEAN` | 躯干过度前倾 | `trunk_lean` 相对本人站立基线 | 最低点窗口 | 腿长比例大者天然更前倾（用个体化基线缓解）；手机机位过高/过低造成透视夸大 |
| `HEEL_RISE` | 脚跟离地 | `heel_rise_ratio` 相对站立基线 | 最低点前后 | 赤足 vs 鞋（鞋跟垫高）；非严格侧视时不可判 |
| `ASYMMETRY` | 左右不对称 | `symmetry_index` on `knee_angle`；`pelvis_offset_ratio` | 最低点窗口 + 组内一致性 | 机位不居中、单侧遮挡、惯用腿差异 |
| `PELVIC_COMPENSATION` | 骨盆代偿 | 髋角与躯干角的耦合突变 | 底段窗口 | **极易误判**——关键点体系不含 ASIS/PSIS，只能代理。v1 只出"提示"，不出"错误" |
| `TEMPO_UNCONTROLLED` | 节奏失控 | 下降/上升时长比、角速度峰值 | 组级 | 慢速练习是有意为之 |

**额状面膝角的重要提醒**：2D 视频对下肢额状面运动的效度存在学术争议（有系统综述结论为"2-D video may not be a valid assessment of lower extremity frontal plane motion"），且同类测量的最小可检测差异约 8°。因此 `KNEE_VALGUS` **输出用"关注 / 明显"两级而非硬性"犯规"**，并在 UI 上弱化措辞。

**这条提醒的适用范围比它原先写的更广，而且原先写的那个码其实没跑起来。** 上表里的深蹲 `KNEE_VALGUS` 用的正是 `frontal_knee_angle_*`，而该特征声明 `views: [frontal]`（`features.dart`），深蹲跑的却是 45° 斜机位 —— 于是它每一帧都在「特征不可用」上跳过，产品里一次都没执行过。**开合跳的 `JJ_KNEE_VALGUS` 是这条判定第一次真正落地**（它的机位就是正面），所以上面那两级措辞与弱化要求对它是硬约束：阈值 `jj.knee_valgus_angle_notice` 取 8° 就是这条最小可检测差异，只出提示级结论、不驱动扣分。

方向上也有一条容易写反的：`frontal_knee_angle_*` 的约定是**直腿 = 0°、内扣越大角越大**，与 `knee_angle_*`（直腿 180°）正好相反，所以越界侧是 `above`。写成 `below` 的表现只是「这条判定老是误报」，看不出病因 —— 两侧各有一条合成帧测试把方向钉死。

### 5.3 组级聚合

单个 rep 的判定汇总为组级评价：

```
完成次数 / 有效次数 / 无效次数
各错误码：出现次数、占比、平均偏离幅度
ROM 均值±SD、节奏均值±SD、对称指数均值
```

组级评级公式框架（**权重与切分待核定，见 §7.3**）：

```
form_score = 100 − Σ 错误码 ( 权重 × 发生率 × 严重度系数 )
```

**未核定的错误码在 v1 只出提示、不进扣分。**

### 6.4 三条设计约束（源自 Laya 的已知缺陷）

1. **候选集必须小。** 错误类型候选 4–6 类、矫正方案候选 5–10 条。超过约 20 个选项后决策准确率急剧下降。
2. **必须选项乱序。** 已知位置偏差（曾有"50 道多选题有 46 道选 A"的报告），所有候选顺序需随机化并记录随机种子。
3. **`score` 原语最弱。** 若严重度打分不稳定，改用多个 `noul` 拆档（如"是否达到中度"）替代单次 `score`。

## 7. 阈值治理

### 7.1 两类参数严格分离

| 类别 | 存放 | 修改权 | 驱动扣分 |
|---|---|---|---|
| **体育阈值** | `server/` 阈值表 | 仅体育专业成员 | 仅 `source_type != pending_review` 者 |
| **工程默认值** | 各模块 `config` | 工程师 | 不参与 |

**工程默认值清单**（可调，非体育结论）：

| 参数 | 默认值 |
|---|---|
| 关键点可见性门控 | 0.5 |
| 短时丢失插值窗口 | 300 ms |
| 长时丢失重置 | 1 s |
| 状态最短停留 | 3 帧 |
| N-of-M 投票 | 5 帧中 4 帧 |
| 伪帧跳变阈值 | 躯干长 × 20% |
| 推理帧率下限 | 15 fps |
| One Euro `minCutoff` / `beta` | 1.0 / 0.02（起点值，需回归调参） |
| 人体包围盒占画面高度 | 55% – 90% |
| 画面边界安全边距 | 3% |

### 7.2 阈值表结构

| 字段 | 说明 |
|---|---|
| `action_code`, `feature_code` | 定位 |
| `standard_group`, `sex`, `age_min`, `age_max` | 分群 |
| `min_value`, `max_value`, `unit` | 数值 |
| `severity_breakpoints_json` | 严重度分档切点 |
| **`source_type`** | `national_standard` / `literature` / `pending_review` |
| `source_url`, `reviewer`, `reviewed_at` | 溯源与核定记录 |
| `version`, `effective_from`, `status` | 版本治理 |

### 7.3 待核定清单（**交付给体育专业成员，禁止工程师填数**）

以下阈值在公开来源中**找不到面向中国学生群体的权威数值**，必须依据国标口径 + 学生群体实测核定：

1. 深蹲「合格深度」的膝角切点、躯干前倾超阈 Δ、脚跟抬升比阈值、左右不对称阈值
2. 膝内扣在**学生人群**的切点与「关注/明显」两级分界；严重度 1/2/3 档位切分
3. 俯卧撑：**实际实现的是四个量**，与本节原先列的几项不完全对得上 ——
   - `pu.min_depth_elbow_angle`（最低点肘角的**上限**）：180° 是全伸直、
     90° 是直角，**越小越深**。定线时要同时给出另一条线：会话分段用的
     `pushupDepthDeg`（工程默认 100°）与它是同一个量上的两条线，
     前者管「这次算不算一次」、后者管「算数的那次够不够好」。
     两条线的次序由 `buildPushUp` 在构造期断言，调换会当场抛。
   - `pu.top_extension_elbow_angle`（撑起时肘角的**下限**）：与上一条共用
     `elbow_angle_L`、方向相反；配套的分段线是 `pushupTopDeg`（工程默认 165°）。
   - `pu.hip_sag_ratio_max` 与 `pu.hip_pike_ratio_min`：`body_line_offset_ratio`
     的**上界与下界**，一个正一个负（正 = 髋更低 = 塌腰）。定线时按「髋相对
     肩踝连线偏离了多少个躯干长」给一个数，**不要按角度给** —— 这个量不是角度。
     注意它在 45° 下读数偏大（分母被方位压缩、分子不被），
     与 `heel_rise_ratio` 是同一类偏差，所以真机标定必须在**产品机位**上做。
   - 原列表里的「体线角切点」对应的是 `body_line_angle`，但那个夹角分不开
     塌腰与撅臀（见 §2.2），本轮改用上面那两个带符号的量。
   - 「肘外展采用值」**本轮不需要**：这个量在侧视/45° 机位下没有可信的值
     （见 §4.3 俯卧撑要点）。
4. 平板支撑：**实际实现的是三个量、四条规则**，与本节原先那一句笼统的「统一采用值」
   对不上 ——
   - `plank.hip_sag_ratio_max` 与 `plank.hip_pike_ratio_min`（撑住的那一段里
     `body_line_offset_ratio` **持续越界**的帧数达到门槛即命中；一正一负，
     正 = 髋比「肩—踝」连线更低 = 塌腰）。**都是带符号的量**，定线时按「髋相对
     肩踝连线偏离了几个躯干长」给数、**不要按角度给** —— 这个量不是角度。
     原列表里那三个文献区间（160–180° / 165° / 178–190°）说的是躯干夹角，
     与这两条判定**不是同一个量**，别直接搬过来。
     两条都必须**严格落在进入线之内**（|阈值| < `plankLineEnterRatio`，工程默认
     0.45）：塌到 0.45 就算「离开支撑位」、这一段当场封存，规则的越界帧数永远攒不够
     —— 这条规则**永远不触发且不报错**，看起来就像「没有人犯这个错」。
     阈值与进入线之间那一段正是它有活干的地方。
   - `plank.elbow_angle_max` 与 `plank.elbow_angle_min`（撑住的那一段里肘角持续
     越界的上下沿）。**两条共用同一个错误码 `PLANK_ELBOW`**：前臂支撑的肘角被几何
     锁在 90° 上下，偏离两个方向都算错，而 `Rule.bad_side` 只有一侧；引擎按错误码
     去重（同一 rep 内重复命中只计一次），所以组级不会翻倍，**不要为了「一码一规则」
     拆成两个码**。两条都必须**严格落在支撑带里面**（`plankElbowMinDeg`＝50° <
     阈值 < `plankElbowMaxDeg`＝130°），否则同上、永远不触发。下沿那条余量最小
     （70° 对 50°）：真机标定若发现撑着的人总是落在这个带的外面，要动的是工程参数
     `plankElbowMinDeg`，**不是**把体育阈值放宽到越出分段线。
   - **三条判定一条基线都不挂**（体线偏移已用躯干长归一、肘角是关节夹角），
     所以标定只采框架强制要求的那两项 —— 这一条不影响定线，但会影响「真机标定
     要在什么姿势下做」：标定时人是站着的。
   - **另有一条不是阈值的实测项**：这个动作是**计时制**，规则门槛
     `minViolatingFrames = 8`（约半秒，其余动作取 2）是按「状态机换相的确认滞后
     会落进窗口尾部」推出来的。真机上要确认的是：**正常收势那几帧不会被读成一次
     塌腰**。若会，要动的是那个门槛或支撑带的边界，**不是**阈值。
   - `PLANK_HEAD` **不做，且不是阈值问题**：它要一个还不存在的特征（耳或眼相对
     躯干长轴的偏角），而现成的 `trunk_lean` 与 `body_line_offset_ratio` 都只用
     肩/髋/踝，头怎么摆完全不进这两个数。
5. 仰卧起坐：**实际实现的是三个量**，与本节原先列的几项不完全对得上 ——
   - `su.shoulder_to_mat_ratio_max`（最低点 `shoulder_height_ratio` 的**上限**）：
     这个量在「臀不离垫」的前提下**上界是 1**（等于 `cos(躯干与竖直的夹角)`，
     见 §4.3），所以它是一把**单边**的尺 —— 越小越贴垫。定线时必须满足两条：
     一是**小于会话分段用的 `situpSeatRatio`（工程默认 0.75）**，否则它永远不触发
     （还没到这条线，这一次就已经不算数了）；二是要容得下国标的收势
     （前倾约 30° → 0.87 的读数在这里对应「贴垫」）。它在 45° 下同样读数偏大
     （与 `heel_rise_ratio` 是同一类方位压缩偏差），所以真机标定要在**产品机位**上做。
   - `su.hip_lift_ratio_min`（整段 `body_line_offset_ratio` 最小值的**下限**）：
     带符号，**负 = 髋高于肩-踝连线 = 顶髋借力**，所以这个阈值是个负数。
     窗口是**整段**（`Phase.ALL`）而不是最低点，原因是坐起途中髋自然高于连线，
     切窗口会把那一段当成顶点 —— 见 §4.3 仰卧起坐要点。
   - `su.knee_angle_max`（整段 `knee_angle_L` 最大值的**上限**）：国标要求屈膝
     约 90°，但膝角在这个动作里是**单边**判据（伸太直才是问题），
     所以只给上限、不给下限。取左膝是因为它写明在规则里，两条腿都算会得到两倍的
     权重（两侧同一件事时，选一侧是约定，不是偏好）。
   - 原列表里的「肘膝距离比」与「抱头距离比」**不做**：两个量都是**接触关系**，
     而 2D 关键点之间的距离在透视下分不出「贴着」与「一臂之遥」（见 §4.3）。
     为它们预留的 `elbow_knee_ratio` / `wrist_ear_ratio` 两个特征也随之不该实装。
     另有一条**不是阈值**的事要在真机上量：门禁的 `tooFarBelow`（0.45）
     对躺姿未标定，而仰卧起坐的起始姿势正是坐着的那一档 —— 见 §4.3 那一条。
6. 引体向上：**实际实现的是三个量**，与本节原先列的那三个名字对得上两个、
   第三个换了一种口径 ——
   - `pullup.dead_hang_min_elbow`（整段 `elbow_angle_L` 最大值的**下限**）：
     定线时**必须大于会话分段用的 `pullupHangDeg`**（工程默认 165°）。原因是
     可推理的：封存一次引体向上的前提就是「肘角回到 165° 以上」，所以每一个被
     计数的 rep，其整段最大值都必然高于它。阈值定在它之下，「最大值越界」恒假
     —— 这条规则**永远不触发、也不报错**，看起来就像「没有人犯这个错」。
   - `pullup.chin_over_dy_max`（**顶点段** `mouth_wrist_dy` 最小值的**上限**）：
     **带符号，阈值是个负数**（负 = 嘴高过腕 = 下颌过杠，见 §2.2）。窗口是顶点段
     （`Phase.APEX`）而不是整段 —— 理由见 §4.3，那是本动作唯一一条会因为遮挡而
     改变结论的判定。定线时要知道那份遮挡容错只是部分有效的，别把它当成
     「读不到就一定有兜底」。**切点必须落在越界侧（> 这个负数）**，
     否则严重度会被降级成 0。
   - `pullup.swing_max_lean_deg`（整段 `trunk_lean` 最大绝对值的**上限**）：
     取绝对值（倾角的符号取决于人面朝画面哪一侧），**绝对阈值、不挂本人站立基线**
     —— 挂在杠上时躯干本来就竖直，与本人站姿习惯无关（与深蹲、跳绳那两条正好
     相反，别为了统一口径把它改成基线偏移）。另要留意它是「整次动作里的最大偏离」
     而不是严格意义上的振幅：引擎的归约只会从窗口里挑一个代表值（min/max/median/anyFrame）、
     算不出峰谷差，
     所以标准动作里躯干在顶点略有后仰会被一并计入，**定线时要把这一段算进余量**。
   - 原列表里的「顶部肘角」**不再是一条阈值**：肘角在这个动作里是**分段信号**
     （工程参数 `pullupTopDeg`，判「算不算一次」），而「这次算不算到位」交给
     `pullup.chin_over_dy_max`。两者合成一条的话，用户就分不清「这一次没算」与
     「这一次算了但过杠不够」—— 同俯卧撑 `TOP` 与 `PU_INCOMPLETE_EXTENSION`、
     开合跳 `OPEN` 与 `JJ_INSUFFICIENT_SPREAD` 的关系。
   - `PULLUP_REST_TIMEOUT` **不做**，且不是阈值问题：它判的是**跨次**的时间间隔，
     属组级计时（见 §4.3）。**全组在杠上吊着不动的那一档也要真机实测**：
     标定要求人在杠上稳住 15 帧，从没在真机上量过一个人能稳多久。
7. 跳绳：**实际实现的是三个量**，与本节原先列的三个名字大体对得上，
   但每一个的口径都要按下面这几条定 ——
   - `rope.buffer_max_knee_angle`（整段 `knee_angle_L` 最小值的**上限**）：
     定线时**必须小于会话分段用的那条封存线** `站立基线 − standing_hysteresis_deg`
     （站立 175° 时是 167°）。原因是可推理的：`CUSHION → GROUND` 的封存条件里
     有一条是「膝角回到站立线附近」，所以**每一个被计数的 rep，窗口里都必然出现过
     接近站立基线的膝角读数** —— 阈值定得比那条线高的话，「整段最小值越界」恒真，
     **每一次计数都会触发**。这是自查这条线定没定错最快的办法。
   - `rope.trunk_lean_max_delta`（`trunk_lean` 整段最大**绝对值**的增量上限，
     相对本人站立基线）：与深蹲、立定跳远那两条同口径。取绝对值是因为符号取决于
     人面朝画面哪一侧，不是体育含义；取「整段最大值」而不是帧计数，是因为跳绳的
     躯干晃动本来就是往复的。
   - `rope.foot_gap_max_ratio`（`foot_gap_ratio` 整段最大值的**上限**）：
     **绝对比值，不挂基线** —— 站定的人左右脚尖本就等高，「基线 × k」≈ 0，
     线落在 0 附近会让每一次落地都命中。原列表里的「左右踝同步容差」在
     **单次判定**这个形状里落地的就是它；而「组内这几跳是不是左右换着落脚」那个
     **跨次**的模式对应 `ROPE_ALTERNATING`，规则引擎对每一次动作独立求值，
     装不下它 —— 见 §4.3 跳绳要点。
     另外这个量是**代理量**，不是足底接触测量：单目视频没有足底接触信息，
     能看见的只有两只脚尖的高度差，UI 措辞不得写成「测到了落地时间差」。
   - 这三条线真机标定时都要在**产品机位**上做，理由同 `heel_rise_ratio`
     那类方位压缩偏差（见第 3、5 条）。
8. 坐位体前屈：**实际实现的是两个量**，与本节原先列的三个名字对不上 ——
   - `srt.knee_angle_min`（**底部段** `knee_angle_L` 最小值的**下限**）：国标要求
     腿伸直，所以这是一把**单边**的尺（越弯越小才是问题），只给下限。窗口是
     `Phase.BOTTOM` 而不是整段，理由见 §4.3。定线时可推理的一条：
     **标定时采到的膝角基线（本人坐直时那条腿）是 175° 上下**，阈值不能定得比
     它还高 —— 那样标准动作会永远命中；也不要比它低太多，否则走形到 140° 还在
     「合格」里。取左膝是约定（两侧同一件事时选一侧，不然权重翻倍）。
   - `srt.ballistic_reversals_max`（**整段** `hip_angle_L` 掉头次数的**上限**）：
     单位是**次数**，不是角度。定线时必须知道两个可推理的端点 —— **一次平稳的
     「下到底再上来」本身就有一次掉头**（`count_reversals` 的第一步只用来定初始
     方向、不计入），所以阈值不能定成 0 或 1，那会把每一次标准动作都判成弹振；
     而死区（`reversalDeadband`＝2°，**工程参数、不是体育阈值**）决定了「多小的
     摆动不算一次掉头」，**定线之前要先确认这个死区**：死区越小、数出来的次数
     越多，同一个人在同一段动作上会得到不同的次数。合成帧上的参照值是
     **弹振 5 次 vs 平稳 1 次**（整段），但真实抖动会让两边都往上走 ——
     这条线必须在**真机**上量，且量之前先定死区。
   - **原列表里的「弹振角速度阈值」不做，而且不是排期问题**：「角速度」要的是
     帧间差分除以时间，而掉头次数只看得见**方向**、看不见快慢（同频小幅的抖与
     同频大幅的抖数出来一样多）。真要做，得先有 `Reduce` 之外的东西 ——
     这一轮刻意只做形状、不做速度，理由是「靠弹振借力」这个错的**证据形态**是
     往复，不是每秒多少度。
   - **原列表里的「并拢距离比」不做**：它要一个还不存在的特征（双手腕间距除以
     肩宽），而按工程约定，加特征 = 两侧实现 + 重生成
     `shared/fixtures/feature_conformance.json` + 两侧测试全绿。这条码
     （双手未并拢）继续留在 `taxonomy.py` 里，理由写在那边。
   - **另有一条不是阈值的事要在真机上量**：站位门禁的 `tooFarBelow`（0.45）对坐着
     的姿势未标定（见 §4.3 仰卧起坐要点里那一段同类记账），而且这个动作**先锁
     横屏**（`ActionSpec.requiresLandscape`）—— 横屏下判据改成「取两个跨度里较大
     的一个」之后，「坐着的人占画幅多少」这个读数要在真机上重新看一眼。
9. 立定跳远：起跳前离地判定、起跳/落地同步容差、缓冲膝角、蹬伸段躯干控制容差。
   **两处口径上要一并定下来**：
   - **「前掌离地」的方向歧义。** 错误码叫 `SLJ_PREJUMP_HEEL_OFF`（脚跟抬起），
     中文名叫「前掌离地」，两者指向**相反**方向。这是有意的：特征只对「脚跟
     抬升」有符号，而学生实际会犯的是两个方向的错（脚跟离地 **或** 前掌翘起），
     所以规则取绝对值 + 与本人站立基线比，一次覆盖两个方向。定切点时按
     「足部离地幅度」这一个量给数，不要给两个方向各定一个值。
       **不要「修正」码名或中文名中的任何一个** —— 改掉任一个，另一个就变成错的。
   - **同步容差是代理量，不是足底接触测量。** 单目视频既没有足底接触信息，
     也无从确认真正的离地/触地时刻；能看见的是两膝不对称，而它同时也是
     「这一跳没被计数」的原因（两腿差得越大，膝角均值越够不到腾空线）。
     因此 UI 措辞不得写成「测到了两只脚落地的时间差」。
10. 开合跳：**实际实现的是三个量**，与本节原先列的四个不完全对得上 ——
   - `jj.spread_min_ratio`（分腿比峰值的**下限**）：`leg_spread_ratio` 已用肩宽
     归一，故用绝对比值；先量几个真人「开到位」的顶点值，再定下限。
   - `jj.arm_min_angle`（**较小那侧**肩角峰值的下限）：180° 是举过头顶。
     注意口径 —— 取左右里小的那个，因为这条问的是「两只手臂**都**举到位了吗」。
   - `jj.knee_valgus_angle_notice`（触地段 `frontal_knee_angle_max` 的上限）：
     **已按学术保留暂定 8°**（见 §5.2 的最小可检测差异），只出提示、不驱动扣分；
     若体育专业成员给出学生群体的实测切点，改这个值即可。
   - 原列表里的「同步容差」**本轮不做**：它对应 `JJ_ARM_ASYNC`，需要一个新特征
     （左右肩角之差），而卡片没有承诺它。落地缓冲与前后漂移则在正面机位下
     **没有可信的量**（见 §4.3 开合跳要点），不是排期问题。
11. **组级评级权重** `w_fault`、发生率-扣分曲线、五级切分
12. 矫正方案的组次剂量（组数/次数/周频/周期）与学段适用性

## 8. 跨语言一致性（本项目最隐蔽的风险）

### 8.1 为什么必须做

特征在 Python（生成训练数据）和 Dart（端侧推理）中各实现一次。**若两者算出的特征存在细微差异，模型会在训练时学到一套分布、推理时见到另一套，准确率静默崩塌且极难定位。**

### 8.2 方案：共享 golden fixtures

`shared/fixtures/` 存放版本化的测试向量：

  "frame_width": 720,
  "frame_height": 1280,

## 附录 A：动作能力边界（必须写进产品文案）

《国家学生体质健康标准（2014 年修订）》共 10 个正式测量项，单目手机摄像头的覆盖情况：

| 覆盖情况 | 项目 |
|---|---|
| ✅ 可完整判定并估算成绩 | 1 分钟仰卧起坐、引体向上、1 分钟跳绳（计数为估算，无法感知绳子） |
| ⚠️ 只能判规范性，**测不出成绩** | 立定跳远、坐位体前屈 |
| ❌ 无法处理 | 50 米跑、800/1000 米跑、50 米×8 往返跑、肺活量、BMI |

> **上表第一行说的是「这个动作的判定能做」，不是「现在什么都做完了」。**
> 已实现的九个动作（深蹲、立定跳远、开合跳、跳绳、俯卧撑、仰卧起坐、引体向上、
> 平板支撑、坐位体前屈）都只做**单次动作的规范性判定与计数**：**国标那种「1 分钟到点掐表」
> 还没做**，所以「估算成绩」那一栏对一个具体的动作而言，现在还没有交付物。
> 卡片文案不许把它说成能做 —— 与「只判规范性，测不出厘米成绩」是同一口径。
>
> **别把平板支撑的「计时制」与上面那句话混起来。** 平板支撑量的是**一次 rep
> 持续了多久**（一段支撑的时长），它是这个项目里第一个 rep 不是「一次动作」的动作；
> 上面说的「1 分钟到点掐表」要的是**一个固定窗口内数了多少次**（计时开始、
> 60 秒后停表、报次数），那是另一件事，仍然没做。两者都叫「计时」，
> 但在数据流上一个是 **rep 的时长**、一个是**组的窗口**，不能互相顶替。

**平板支撑不在国标那 10 个测量项里**，列在这里是因为它同样受单目约束，
而且它的边界与俯卧撑那条同源：**「趴着的人」与「真的撑着的人」在单目投影下同形**
—— 两者的差别只有「身体离地多高」，而单目没有深度参照（同「立定跳远测不出厘米」
那条）。所以它也只能判规范性：**撑了多久**与**每段里塌腰/拱起/肘角偏离几次**。
`PLANK_HEAD`（头颈位置）另外受限于一个还不存在的特征，不是精度问题。

**其中五个动作（立定跳远、仰卧起坐、坐位体前屈、俯卧撑、平板支撑）在端侧要横着做**
—— 不是因为要量长度，而是这五项做动作时身体是**横着铺开**的，竖直画面高而窄、
必然把头与脚各切掉一端（见 `ActionSpec.requiresLandscape` 与 `app/README.md`
的「横屏与方向」）。**这不改变上表任何一行**：判定能力与画面方向无关，
横屏只是让那几项够得着「全身入画」这条前提。

**原因**：立定跳远/坐位体前屈需要绝对距离，单目无标定不可测；50 米跑需要起终点同步，两台设备时钟误差远大于 0.1 秒的精度要求；肺活量需要专用仪器；BMI 需要身高标定。

**产品定位**：本平台是「动作规范性判定 + 纠错训练」，不是「体测成绩测量仪」。成绩由用户录入或体测设备导入，平台负责评分换算与薄弱项分析。
